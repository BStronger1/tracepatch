## 工程与任务准备

[结构化 Python 工具](../docs/PYTHON_CHECK_TOOL.md)采用独立监督进程，直接执行 Agent 提供的 Python 代码，
不借助外层 shell 判定成功。返回进程状态、超时、测试代码哈希和执行前后源码版本，
长输出只截断内容，保留状态和合法 JSON。Agent 自写检查始终不属于独立验收，不会自动提交。

77 项本地离线测试通过。[无 API Docker 集成](python-tool-docker-001.json)验证七种情形：
打印成功但断言失败、打印提交标记但不提交、超时、长输出、源码变化、伪造状态文本、信号终止。
这些验证的是工具行为，不是模型采用或修复效果。

[新任务](../docs/CLICK_FORWARD_TASK.md)源自 [Click PR #1840](https://github.com/pallets/click/pull/1840)。
十组验收在调用前冻结；[预检查与回归注入](forward-task-check-001.json)确认错误版失败、参考版全过，
并能识别父上下文污染、过滤未声明参数、错误覆盖显式值三类人为缺陷。
它是历史公开问题、参考修复较小，不代表复杂企业级任务；作者查看了参考修复，不是盲测保留集。
当前覆盖两个仓库、五个不同历史问题，Cookie v2 不重复计数。

## 实际采用与补丁审计

新工具组全部 24 个动作均选择 bash，没有形成可供模型运行审计的 python_check 记录。
长时间查看源码后，它在最后一次动作尝试替换一个不存在的代码片段，`assert old in s` 失败，
既有源码未改变。随后查看源码的命令又令外层返回零，说明可选工具并未覆盖这条仍采用 shell 的执行路径。
工具说明送达不等于工具被使用；不能把本轮当作新工具已实测改善测试判定的证据。

普通工具组的补丁虽然通过冻结回归，却修改了通用子上下文创建和 forward 的参数签名。
具体疑点触发了[两个事后离线诊断](forward-posthoc-audit-001.json)：

- 普通 `invoke` 把未显式传入的父参数带进子上下文，造成上下文与实际收到参数不一致。
- 将 `forward(*args, **kwargs)` 改为命名 `self, cmd` 后，业务参数恰好名为 `cmd` 时发生重复绑定错误；诊断还携带 `self` 业务参数。

参考修复通过两项诊断，普通工具组一项失败、一项错误；新工具组因保留错误基线而有一项失败。
这是基于补丁审查新增的诊断，不追改冻结的十组成绩，不把事后发现放回模型提示，也没有再次调用模型。
诊断提示当前验收仍有覆盖缺口；全上游测试、更多 Python 版本及更广行为均未验证。
