# 公开检查来源与版本反馈：首次冻结对照

2026-09-26。Requests Cookie v2 已知开发题，各运行一次 observe 与 feedback。
**两组公开复现均通过，独立回归均为 9/10，均未正常提交。**
反馈链路与版本绑定得到验证，本轮没有观察到最终修复或提交改善。

## 实现与检验

新增[公开检查](../docs/PUBLIC_CHECKS.md)：宿主机冻结公开脚本，按允许的既有 Python 文件重建候选，
对初始及每个新的源码版本在新建断网容器中直接运行检查进程。
脚本哈希、源码集合哈希、真实进程退出码与输出哈希一并记录；结果未知时不沿用旧通过状态。
Agent 修改其容器中的复现脚本，不会改变宿主机冻结副本。

70 项离线测试通过。[无 API Docker 检查](public-checks-docker-001.json)覆盖错误基线、参考版、
Agent 伪造的复现脚本、被后续命令掩盖的失败退出码及冻结脚本变化。
集成脚本首次因相对输出路径被 Git 按上游目录解析而失败，未调用模型；修正为绝对路径后通过。

不向 Agent 提供独立验收或参考补丁。模型仅看到公开检查的状态、源码及脚本哈希、
不同测试来源的说明、复查冲突建议与单独提交提醒。公开检查没有自动提交权限。
这组反馈包含多个成分，不能分别归因于版本哈希或某句提醒。

## 冻结条件

[计划](public-checks-plan-001.json)在调用前冻结实现、任务与配置；
[机器报告](public-checks-study-001.json)核对唯一计划差异是 `check_mode`。
顺序 observe → feedback，每组一次，无中途调参、重试或验收器变更。

两组同为 qwen3.8-flash、recovery-submit、原生 bash 工具、recent-turns、
公开复现、24 次调用上限、1024 输出 Token、24000 字节请求上限、4200 字节记忆上限、
structured 记忆、仅记录源码进展、固定 Python 3.9 镜像与源码。
两组执行相同版本检查流程，只在 feedback 追加当前结果和建议。
所有预检查符合预期：错误版失败、参考版通过。

## 失败分析

observe 候选通过重新调用 `type(jar)(policy=policy)` 构建容器，
遇到不接受 `policy` 参数的子类时失败。独立回归中对应一项 TypeError。

feedback 候选调用 `copy.copy(jar)`，但所在模块没有导入 `copy`；
宽泛的 `except Exception` 掩盖该错误，转而尝试 `type(jar)(jar._policy)`。
在独立用例中，策略对象被误当作子类的业务参数，原本应保留的 `label='retain-me'` 丢失，
对应一项断言失败。此结论来自保存的最终源码与独立验证栈，不修改原补丁或成绩。

feedback 最后仍在运行自写测试；输出含 AssertionError，外层退出码却为 0。
命令用“成功字符串出现次数”作为退出码，没有出现成功字符串时得到零，逻辑颠倒。
Harness 保留原始工具结果，没有把它算作测试通过；提交标记未发出，随后调用耗尽。
这说明仅追加来源说明与提交提醒，尚未解决 Agent 编写测试命令及遵守收尾协议的问题。

## 可写与不可写

可写：实现公开脚本冻结、源码版本绑定、隔离检查、来源区分及受控反馈；
通过冻结对照和失败轨迹审计，验证反馈送达并发现公开复现与独立验收不一致的案例。

不可写：提升修复成功率、提升提交率、降低费用、可靠跨仓库修复。
仍为两个仓库四个历史问题；本轮没有增加独立题目数量。
每组一次、已知开发题、多成分反馈、历史公开修复可能已进入训练数据，均限制结论。
进程退出零也不能防范恶意候选代码提前退出；这是来源与执行隔离机制，不是防篡改证明。
