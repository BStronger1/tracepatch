# 逐步源码观测与复查提示：首次配对实验

2026-09-26。新增进展观测和可选提示，在已用于开发的 Click 历史问题上各运行一次。
**两组均未修复、均未提交。** 本轮证明采集、触发和提示接入可运行，未证明修复质量提升。

## 实现与预先固定的条件

每次执行动作后对允许导出的既有 Python 文件计算指纹，记录逐步变化、相对起点的净变化、
连续未变化次数及采集异常。命令字符串不同不会规避相同源码状态的观测。
采集失败打断连续计数，不把未知当作未变化；改后撤回可通过净变化辨别。
工具退出码不作为可信测试成绩。详见[设计与复现](../docs/PROGRESS.md)。

47 项本地离线测试通过。[Docker 集成检查](progress-docker-check-001.json)包含 13 个合成动作，
覆盖连续阅读、修改后返回失败、替换失败、撤回、删除、符号链接拒绝、恢复采集及提交异常传递；
没有模型调用，不计入真实修复成绩。

[冻结计划](progress-plan-001.json)在模型调用前保存任务、验证器、实现和配置哈希。
两组共享：qwen3.8-flash、原生工具调用、recovery-submit、有界最近历史、24000 字节请求上限、
1024 输出 Token、24 次调用上限、公开最小复现、相同源码与 Python 3.9 镜像。
独立十组回归和参考修复不提供给 Agent；两组预检查均确认错误版失败、参考版通过。

- observe：只采集，不发送进展提示。
- feedback：同样采集，每连续 6 个动作源码未变化，在下一请求发送一次复查提示。

顺序预先固定为 observe → feedback，各一次，无自动重试、未因失败追加运行。
代码与任务未在两组之间修改。[机器报告](progress-study-001.json)确认仅 `progress_mode` 不同。
提示占用原有上下文额度，可能改变历史保留量；这属于该干预的实际作用范围。

## 补丁与失败证据

只记录组修改 `src/click/core.py` 和 `src/click/types.py`，首次修改较晚；
补丁在 Parameter 初始化中引用未定义的 `attrs`，独立验证发生 NameError。

提示组三次修改 `src/click/core.py`。最终把推断逻辑移入 Option 初始化，
但引用该作用域未定义的 `nargs`，最小复现和独立验证均失败。
最后一个动作看到了这个错误，剩余调用已耗尽，未正常提交。

此前只有最终补丁的轨迹不能追溯生成逐步源码状态。旧 Click 运行中“前 21 个动作主要在阅读”
是人工审阅线索，本轮的新快照才支持“连续 21 / 18 个动作边界源码未变”的观测结论。
这不证明这些阅读都无价值，也不证明首次修改提前由提示造成。

## 可支持的结论与下一步

可以说已实现逐动作源码观测、未知状态处理、可选恢复提示和冻结配对评估。
不能说“消除停滞”“修复成功率提升”或“缩短修复时间”：两组均失败，提示组总耗时也更长。
每组仅一次、同一已知开发题，没有独立保留集或统计稳定性；不是 SWE-bench 成绩。
只验证自定义回归，没有运行完整 Click 上游测试套件。

单独催促修改不足以保证正确性。下一方向是保存并恢复关键源码位置与失败检查证据，
让下一次修改有明确依据，再设计新版本的对照；不直接修好评估题替代 Agent 的工作。
