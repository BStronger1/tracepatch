# 十六次运行的离线结果归类

范围为证据记忆、完整签名、公开检查、Python 工具、阶段调度、新补全任务这六个连续阶段的全部配对运行，
共 16 次；各阶段的任务、验收版本和配置不同，不能合并为某一策略的成功率。
更早的实验未纳入本表，不删除或改变其记录。

使用 [离线归类工具](../scripts/audit-failures.py)读取保存的 JSON 元数据，
结果与文件哈希见 [机器报告](failure-inventory-001.json)，规则见 [分类说明](../docs/FAILURE_TAXONOMY.md)。
没有重新执行历史轨迹或调用 API。该工具描述保存的证据，不独立认证日志真实性或判断根因。

| 记录类别 | 次数 |
| --- | ---: |
| 修改后验收失败、未提交 | 10 |
| 已提交但验收失败 | 2 |
| 验收通过但未提交 | 1 |
| 冻结验收通过且提交 | 2 |
| 观测完整但没有记录源码修改，验收失败 | 1 |

其中 3 次当前公开复现通过，但独立验收失败；
2 次运行出现 Python 检查内部改写源码。
这些附加观察与上表类别重叠，不能相加作为更多运行，也不能解释为发生频率的总体估计。

“冻结验收通过且提交”的两次中，Click forward 普通工具组事后仍发现两个兼容性缺陷，
见 [原报告](forward-tool-study-001.md)。自动归类器不会发现测试未覆盖的问题，也不会用事后验收追改原分数。
另一次是阶段实验的 Requests observe，当前十组冻结验收通过；未验证全部上游行为。

从这些个案可以确定：项目需要分别保留格式拒绝、源码变化、检查来源、验收与提交证据。
仅统计“工具成功”或“任务已提交”会混淆不同结果。
不能据此确定遗忘、模型能力或提示是失败的主因；那需要新的受控实验。
