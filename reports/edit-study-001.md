# 结构化编辑首次对照与换行缺陷修复

本轮实现可选 `replace_text(path, old, new)`，在同一个已知 Click 开发题上完成固定对照。
**两组都没有形成补丁。开启组两次调用编辑工具，但暴露了工具自身的 CRLF/LF 兼容缺陷。**
随后修复工具并通过离线及 Docker 回归；没有重跑模型或覆盖原成绩。

## 冻结设计与结果

- 同为 qwen3-coder-plus、Click 2040，先关闭后开启，各一次；上限 24 次调用、1024 输出 token、24000 输入 JSON 字节。
- 相同底座、任务、镜像、模型报价与执行策略；原生调用、结构化记忆、公开检查反馈、Python 工具开启，阶段仅观测。
- 开启组增加工具 schema 和固定编辑说明，属于完整接口干预。采样使用服务商默认，无显式温度或种子。
- [冻结计划](edit-plan-001.json)在 API 请求前写入；[完整审计](edit-study-001.json)核对所有请求、版本、阶段决策、工具记录、成本与严格对照条件。

## 从日志状态到字节证据

开启组动作 13、18 均返回 `old_text_not_found`，两个 old 参数相同。
只看状态，不能直接认定模型复制错误：包内文件实际含 581 个 CRLF，参数使用 LF。
原始字节匹配为零，仅转换换行后，两次输入均唯一匹配。函数其他内容无差异。
[只读换行审计](edit-newlines-001.json)核对候选文件与初始哈希相同，不执行轨迹中的命令。

关闭组两个 Python 检查虽返回进程成功，但一个只求值列表，另一个只打印列表，没有成功断言。
包内源码和公开复现仍失败。这说明进程成功不等于修复验收通过。

此前另一次 Coder 运行的备份、空 diff、临时命名空间问题是设计动机，
不是本轮失败的解释。见 [此前动作审计](edit-motivation-001.json)。

## 修复与复现边界

初版要求字节级原文匹配。修订版仅对统一 LF/CRLF 的源文件转换输入换行，
保留原文件格式；其他字符、唯一匹配、语法、路径、链接和落盘哈希检查继续保留。
混合换行不隐式转换；结果明确标注匹配模式与原文件格式。

108 项离线测试通过；[第二次 Docker 检查](edit-docker-002.json)确认 LF 参数编辑 CRLF 文件、
实际导入值改变、换行保持不变，并复查原有拒绝与提交边界。全部使用合成响应，零 API 请求。
[初版 Docker 检查](edit-docker-001.json)当时只覆盖 LF 文件，未能发现真实仓库的换行问题。
