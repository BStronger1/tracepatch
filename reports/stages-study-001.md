# 阶段调度：两仓库固定对照

本轮验证了按源码与检查证据安排工具的实现，但没有观察到修复或提交改善。
Click 两组均失败；Requests 只记录组通过十组冻结验收并提交，引导组为 8/10、未提交。
每题每组只有一次，不能据此认定阶段调度普遍有益或有害。

## 协议与实现

[预先冻结的计划](stages-plan-001.json)固定所有执行模块、任务、模型配置及运行顺序；
[机器可读报告](stages-study-001.json)包含严格条件比较、逐请求决策、检查元数据与轨迹哈希。
四次运行之间未修改这些文件，没有挑选重跑或自动重试。

两组均提供 bash 和 python_check，采用相同的原生调用、有界历史、结构化记忆及公开检查反馈。
observe 只记录阶段；guide 发送阶段建议，并在缺少版本匹配检查时指定 Python 工具。
干预包含阶段提示与工具路由，不能归因于某一句提示或单个组件。
最多 24 次模型调用，单次输出上限 1024，输入上限 24000 字节；模型为 qwen3.8-flash。

先运行 Click observe / guide，再运行 Requests guide / observe。顺序对调，但没有随机化。
Click v2 在旧十组基础上加入两项已公开的兼容性契约，错误版失败、参考版十二组全过，见
[预检查](click-v2-preflight-001.json)。保留原任务和成绩，当前仍为两个仓库五个不同历史问题。
这些是已知开发题，不是独立保留集或官方基准。

阶段规则及复现命令见 [STAGE_GUIDANCE](../docs/STAGE_GUIDANCE.md)。
86 项离线单元测试通过；[无 API Docker 集成](stages-docker-001.json)用合成回复验证错误工具在执行前被拒绝、
修改后重查和显式提交协议。它不属于模型修复成绩。

## 轨迹与补丁分析

- Click observe 先完成两次退出零的自写检查，动作 20 才修改 forward；没有修复 invoke 的参数记录，且命名 self/cmd 与业务关键字冲突。退出零的自测没有覆盖这些要求。
- Click guide 首次修改提前至动作 11，但最终 forward 把绑定的 Context 当成目标 Command，且没有修复 invoke。提前修改没有带来正确补丁。
- Requests observe 在第 19 次调用显式提交，十组冻结验收通过。该候选重建 Cookie 属性和容器副本；这仅支持本次冻结验收结果，不能证明所有上游行为或子类均兼容。
- Requests guide 到动作 19 才修改。最终对 RequestsCookieJar 使用浅复制，仍共享 Cookie 对象；独立验收中的对象独立性与元数据复制检查失败。

Click guide 的第三次 Python 工具调用（动作 18）实际执行了源码替换，虽然进程退出零，但源码前后哈希不同。
系统将记录标记为 changed，下一次请求仍要求检查新版本；动作 19 的检查失败。
这一真实轨迹验证了“测试期间修改源码不构成最终版本检查”的处理路径，不能解释为修复质量提升。
它也说明工具名称及提示无法保证模型写出的代码确实是有效测试。

离线审计从保存的源码版本和动作记录重新计算了全部 **91 次阶段决策**，与记录逐项一致；
六次指定工具请求均实际执行 Python 检查。检查代码、输出及前后源码哈希一致。
独立验收没有进入 Agent 提示或调度判断，也没有因自测通过而自动提交。

## 结论与项目表述

可以描述：实现并评估可关闭的阶段调度，结合源码指纹和检查来源安排验证，
通过原生工具选择及适配器校验落实检查节点，保留逐请求决策以便离线复核。
不能描述为提高成功率、减少成本或解决长期阅读问题。

这轮对照说明，安排检查能使指定调用发生，但检查质量、实现正确性与收尾仍需分别评估。
后续应先整理失败类型及覆盖缺口，再设计更广的独立任务或模型对照；不能继续围绕同两题调整并选择成功结果。
模型能力差异是待检验假设，本轮不足以将失败归因于模型。
