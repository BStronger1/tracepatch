# 证据记忆：两个仓库的冻结配对实验

2026-09-26。实现按源码版本失效的证据卡片，在 Click 和 Requests 各运行一组
“仅采集 observe / 补回 recall”对照。**四份补丁均未全部通过独立验证；本轮没有证明修复成功率提升。**
两份 Requests 补丁虽然正常提交，仍被独立检查拒绝。

## 实现与验证

新增源码位置和失败记录卡片，绑定动作、输出哈希及源码指纹；实际注入的内容另存本地以便审计。
代码变化后旧卡片标为过期，无法确定日志版本时标为未知，均不补回旧片段。
系统提示、任务、最新完整工具交互和卡片共同遵守原有 24000 字节上限，
不额外调用模型总结。详见[设计及复现](../docs/EVIDENCE_MEMORY.md)。

- 57 项本地离线测试通过，包含版本失效、采集竞态、失败保留、卡片容量、原生工具配对、
  额度不足时舍弃卡片及注入内容的完整性检查。
- [Docker 检查](memory-docker-check-001.json)以五个合成动作验证采集、代码修改、旧记录过期、重新读取与补回。
- 新增 `scripts/demo-memory.py`，无需 API、Docker 或上游仓库，可运行合成机制演示；也加入双平台 CI。
  合成结果不计为模型修复成绩。

当前源码采集只识别简单只读链中的数字 sed 范围，每次最多三个范围、每范围前 16 行且不超过 700 字符。
不推断复杂 grep 输出或动态脚本的源码位置。失败记录包括非零命令和 Python 错误行，
并非每条都是目标任务的测试失败。采集是确定性规则，尚无语义相关性排序。

## 冻结条件

[计划与哈希](memory-plan-001.json)在首次模型调用前保存；[机器证据](memory-study-001.json)包含逐次成绩、
调用指标、卡片状态、注入哈希和同条件比较结果。四次运行中没有修改任务、验证器、模型或实现。

每题两组共享：qwen3.8-flash、原生工具调用、recovery-submit、最近完整历史、公开最小复现、
1024 输出 Token、24 次调用上限、固定源码与 Python 3.9 镜像。每题各有十组独立回归，
运行前错误版失败、参考版通过；参考修复与独立验证器不进入 Agent 容器。

两组均采集进展和证据，**均关闭进展复查提示**。唯一计划干预是 `memory_mode`：
observe 不补回卡片；recall 在需要删减历史时补回最多 4200 字节的卡片消息。
补回会占用总预算并可能挤掉更多早期对话，这属于该干预本身。

预先固定顺序：Click observe → Click recall → Requests recall → Requests observe。
每题每组一次，无自动重试，没有在看到失败后追加运行。两题都曾用于开发，不是独立保留集。

## 结果

| 指标 | Click 仅采集 | Click 补回 | Requests 仅采集 | Requests 补回 |
| --- | ---: | ---: | ---: | ---: |
| 全部独立验证通过 | 否 | 否 | 否 | 否 |
| 正常提交 | 否 | 否 | 是 | 是 |
| 模型调用 / 执行动作 | 24 / 24 | 24 / 24 | 24 / 23 | 24 / 24 |
| 首次源码修改动作 | 19 | 23 | 14 | 8 |
| 采集源码卡片 / 失败卡片 | 1 / 6 | 13 / 5 | 3 / 5 | 4 / 6 |
| 实际补回请求 | 0 | 18 | 0 | 16 |
| 历史删减请求 | 15 | 18 | 15 | 16 |
| 截断拒绝 | 0 | 0 | 1 | 0 |
| 运行耗时（秒） | 107.937 | 81.515 | 142.515 | 118.187 |

四组源码采集错误均为 0。两组 recall 的 34 次注入均处于实际发生历史删减的请求中，
所有请求均未超过 24000 字节，没有因记忆卡片无法容纳而回退的情况。

实际注入的卡片累计出现 131 次：版本匹配 108 次、过期 22 次、未知 1 次，
这是跨请求的出现次数，**不是 131 条独立知识**。过期和未知卡片只提供历史位置、类型与状态，不带旧片段。
注入正文的哈希按读回并规范化换行后的 UTF-8 文本核对；原始正文、源码片段和工具日志只留本地。

## 失败与边界

- **Click 仅采集**：补丁引用未定义的 `multiple`，十个测试方法产生 2 次断言失败、11 次错误（含子测试）。
- **Click 补回**：只修改了列表默认值的类型推断；重复标量元组默认值仍被视为多参数选项，
  出现要求两个参数等行为错误，共 9 次断言失败。补回没有解决核心语义问题，首次修改反而更晚。
- **Requests 仅采集**：十组中两组失败，复制时丢失自定义 CookieJar 类型和原策略。
- **Requests 补回**：十组中一组错误，补丁直接调用 `type(jar)(policy=...)`，
  不兼容不接收 `policy` 参数的自定义构造函数；虽然已提交，依然是失败补丁。

不将 Requests 的失败项减少或运行耗时变化表述为稳定收益：每个条件仅一次，
模型运行存在变化，两个任务的首次修改方向也不一致。没有官方基准分数或统计显著结论。
没有运行完整上游测试套件，历史公开修复也可能进入过模型训练数据。

可以写入项目经历的是：实现有版本和来源的证据记忆、上下文内的有界补回、
失效与未知处理、完整注入审计及两个真实仓库的配对评估。
目前不能写“提高成功率”“降低遗忘率”或“可靠跨仓库修复”。

接下来应检验两类具体限制：采集是否覆盖关键函数与任务约束，以及补回内容是否导致有效的验证和修改。
数字 sed 范围前 16 行可能缺少完整签名或逻辑，版本匹配也不代表内容相关；
不应继续只靠增加卡片或重复调用来宣称改进。

本轮 96 次 API 调用，按既有报价估算 **0.378321255 元**，没有未知费用请求；不是提供商账单。
