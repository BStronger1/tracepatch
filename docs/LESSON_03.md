# 第三课：开发集、原始策略与预算账本

这一阶段回答：原始 Agent 究竟在哪些任务和步骤失败？先观测，再设计策略。

## 三个自建开发任务

| 任务 | 待修复问题 | 观察方向 |
|---|---|---|
| config-precedence | 配置优先级、零值与非法端口 | 能否根据明确约束覆盖边界情况 |
| long-log | CSV 引号、逗号、转义；诊断日志中间有证据 | 是否读取长日志、是否找回被截断证据 |
| retry-contract | 重试次数、异常传播与异常对象保留 | 是否使用测试反馈修正行为 |

它们是受控教学/开发题，不是企业真实问题或标准 benchmark。任务名称是设计意图，不代表实际触发了长上下文或死循环。尤其 retry-contract 测试的是待修复程序的重试逻辑，并不自动证明 Agent 自身出现盲目重试。

## 独立验证

每题先检查错误实现失败、参考实现通过。Agent 只拿到 workspace 与任务说明，看不到 verify.py 和 oracle.py。运行结束后只把 solution.py 拷入新的无网络容器，用固定外部测试验证。此方法隔离测试修改和环境残留，但尚不是对恶意规避测试的完备防护。

## 固定基线

原始执行循环来自固定版本 mini-swe-agent；我们只增加必要的接口适配、严格文本动作解析和实验记录。每题最多 8 次请求、单次最多 512 输出 Token、工具观察截断为前 6,000 字符。没有开启新的上下文管理或恢复策略。

这项截断限制可能成为后续研究对象，不能把修复我们自己人为设置的限制夸大成通用能力提升。

## 预算

账本位于 artifacts/budget-ledger.json。为先前请求保守预留 1.2 元（不是已花费 1.2 元）；后续每次请求发送前预留 0.1 元。进程崩溃或费用未知不会自动退款，也不自动重试。累计预留到 10 元即拒绝新请求。

输入字节数与最大输出数都有上限，预留按现有报价保守设置；实际账单仍由供应商计费决定。密钥不进入账本、容器或报告。

## 如何读结果

1. manifest.json：固定版本、任务内容哈希、提示词与执行参数。
2. preflight.json：题目有效性的证据。
3. 每题 trajectory.json：动作、反馈、退出原因。
4. 每题 patch.diff 与 result.json：修改内容、外部验证、错误类型与费用估算。
5. summary.json：所有已执行任务；若批次中断，未执行题目不能算作成功或从分母静默消失。

请从失败轨迹指出：哪一步、什么证据、可能是什么原因。若三题全部通过，就说明暂时没有足够失败证据，应增加任务覆盖，而不是立即宣称策略有效。
