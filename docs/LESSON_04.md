# 第四课：为什么工具调用完整，比多跑几轮更重要

这份说明用于项目完成后的讲解，不要求先做作业再继续开发。

## 你这个项目研究的是什么

模型负责提出操作，例如读文件、修改函数、运行检查；mini-swe-agent 负责把操作串起来。
TracePatch 管理这条执行过程：检查操作是否完整、控制上下文和预算、保存失败证据，
再用独立测试判断补丁是否符合任务要求。模型通过 API 在服务端运行，代码执行和验证在本机 Docker 中完成。

你没有训练一个新模型。你的项目是围绕已有模型建立可验证的 Coding Agent 实验工具，
并研究执行过程中的限制与失败，这正对应岗位里的 Agent Trajectory 分析、Evaluation 和实验迭代。

## 两种“长度限制”不同

**输入限制**控制这一轮能带给模型多少材料。项目按请求 JSON 字节数限制输入，
超限时保留原始任务与最近完整的调用—结果对，移除较早交互，并记录删减信息。
字节数只是本项目的约束方式，不等于模型的 Token 数或服务商真实上下文窗口。

**输出限制**控制模型这一轮最多能生成多少 Token。如果模型试图一次写一大段修改命令，
可能在参数还没写完时被截断。项目看到 `finish_reason=length` 就拒绝执行，
即使回复看起来像完整命令，也保留同样的拒绝规则。

所以，增加允许调用的次数并不一定解决问题：每一轮若都写不完命令，更多轮次仍可能失败。
提高输出额度也不是万能修复，它可能增加成本，还需要检查是否真正改善补丁和提交。

## 怎样证明一次调整有作用

先固定题目、代码版本、独立测试、模型、提示和运行策略；只改变要研究的输出额度。
每档重复运行，并保留所有结果。记录至少三个不同事实：

1. **能不能执行**：回复是否完整、工具参数是否合法。
2. **有没有修好**：导出的补丁是否通过独立回归。
3. **有没有完成流程**：模型是否在限制内正常提交。

“模型说完成了”和“测试全部通过”都不能单独证明完整修复。前一轮重定向题的补丁通过了
预设测试，但额外审计发现它吞掉一个本来合法的自定义参数。原始测试成绩保留，新增缺陷也报告，
这样别人才能判断测试覆盖的边界。

## 面试时可以怎样解释

“我基于现成 Agent 底座搭建了执行诊断和独立验证流程。分析真实轨迹时发现，失败不全是模型不会修代码，
也可能来自命令输出截断、工具协议错误或没有在剩余步数内提交。我把这些状态分开记录，
再通过固定任务和运行快照做小规模对照。还遇到过通过既定测试却引入新缺陷的补丁，
因此我同时保留冻结评估和事后审计，避免过度解释分数。”

代码由 AI 辅助开发，正式面试前需要亲自理解并能修改关键部分；按自己实际承担的设计、验证和分析工作表述。
具体数值以[输出额度实验报告](../reports/output-budget-study-001.md)为准；
两次重复、单个历史问题不能证明跨任务或跨模型的普遍提升。
