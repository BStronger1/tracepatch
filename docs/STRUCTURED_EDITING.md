# 结构化源码编辑

`run-repo.py --edit-tool replace` 可选启用 `replace_text(path, old, new)`。
默认关闭，启用需同时开启原生工具调用、Python 检查与源码进展观测。
工具使用原任务的已有包内 Python 文件清单，不允许创建新文件。

模型明确选择相对路径、原文和替换文本；工具要求原文唯一匹配（包括重叠匹配），
检查候选 Python 语法，通过后使用同目录临时文件原子替换，并读取实际落盘内容计算哈希。
路径不在清单、链接、原文缺失或多处匹配、无变化、语法错误均返回明确状态。
每次输入和结果留存在本地 `edits/` 中；返回的文件前后哈希与逐动作源码观测可相互核对。

这是单文件编辑接口，不是跨文件事务，也不是对恶意后台进程的完整安全隔离。
语法检查不会执行候选代码，不能发现未定义名称、错误逻辑或兼容性回归。
`applied` 只说明替换已落盘；公开复现、自写测试、独立验收与显式提交仍分别记录。
模型仍可选择 bash 或 Python，工具可用不代表实际采用，更不代表修复有效。

## 设计依据

此前 `repo-model-completion-coder-001` 的 Click 运行中，动作 21 复制包内文件作备份，
动作 22 比较两份相同文件；动作 24 将尝试修复写入临时文件、在检查进程里执行。
实际包内源码全程未变，而且临时命名空间中的函数替换没有接入原模块的调用路径。
因此同时存在落盘位置和实现连接问题，不能把全部失败归因于缺少编辑工具。

本轮固定同一个模型、同一个已有开发题，对比关闭和开启编辑工具。
开启组同时增加工具描述和固定使用说明，属于完整编辑接口干预；不能拆成某一句提示的独立效果。
每组一次，保留失败、不按成功挑选重跑，不据此声称稳定收益。

## 本地验证

单元测试覆盖输入协议、唯一匹配、越界路径、语法错误、哈希与异常状态。
`scripts/check-edit-tool.py` 使用合成 API 回复经过实际适配器，在真实 Docker 中编辑、
逐动作采集、检查落盘结果和链接拒绝；只在显式提交动作中结束任务。
该检查不调用模型，不能作为模型修复成绩。结果见 `reports/edit-docker-001.json`。

## 首次实测后的换行修正

首次实测两次原文匹配失败，经逐字节核对，差异只有文件 CRLF 与工具参数 LF。
这属于编辑接口兼容缺陷，不能归为模型提供了错误的函数内容。
保留原冻结计划、运行快照及成绩；随后修订只对统一 LF 或 CRLF 文件将输入换行转换为
原文件格式，其他字符仍须完全一致。混合换行文件不做隐式转换。
结果标注 `match_mode` 和 `source_newline_style`，哈希仍对应实际输入与实际文件字节。
新增单元测试及 Docker 检查见 `reports/edit-docker-002.json`。
修订版未重跑付费模型实验，不能用原实测评价其效果。
